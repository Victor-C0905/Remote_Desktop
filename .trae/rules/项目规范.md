# GNOME 远程控制客户端 — 完整方案

> 版本: v1.1 | 日期: 2026-05-29
>
> 核心理念：以 GNOME 设计系统（Adwaita）和交互模式为基石，构建一个本地运行的、系统级 UI 质感的远程 Linux 服务器控制客户端。

---

## 〇、架构分层规范（强制执行）

> **所有代码必须遵循以下分层规则，不得违反。**

### 0.1 前端职责（React + TypeScript）

| 职责 | 说明 | 示例 |
|---|---|---|
| **UI 渲染** | 组件渲染、样式、动画 | `Desktop.tsx`, `FileManager.tsx`, `Terminal.tsx` |
| **用户交互** | 事件处理、表单验证 | `onClick`, `onChange`, `onSubmit` |
| **状态管理** | React Context、useState | `ServerManagerContext`, `WallpaperContext` |
| **调用后端** | 通过 `invoke()` 调用 Rust | `invoke("read_dir")`, `invoke("remote_connect")` |

**禁止在前端做：**
- ❌ 直接访问文件系统（必须通过 `invoke("read_dir")`）
- ❌ 直接建立网络连接（必须通过 `invoke("remote_connect")`）
- ❌ 处理敏感数据（Token、密码必须存储在 Rust 后端）
- ❌ 执行系统命令（必须通过 Rust PTY 管理）

### 0.2 后端职责（Rust + Tauri）

| 职责 | 说明 | 示例 |
|---|---|---|
| **系统操作** | 文件读写、进程管理 | `read_dir`, `spawn_terminal` |
| **网络通信** | QUIC/WebSocket 连接 | `remote_connect`, `remote_read_dir` |
| **安全逻辑** | Token 管理、权限检查 | `connection.rs` 中的认证逻辑 |
| **数据转换** | 序列化/反序列化 | `Envelope` 编解码 |

**后端必须提供：**
- ✅ 所有系统操作通过 Tauri Command 暴露
- ✅ 网络连接状态管理
- ✅ 错误处理和日志记录
- ✅ 安全的 Token 存储（localStorage 前端可读，但验证在后端）

### 0.3 调用模式

```typescript
// ✅ 正确：前端通过 invoke 调用后端
const entries = await invoke("read_dir", { path: "/home/user" });

// ✅ 正确：根据连接状态选择本地或远程
const entries = activeServerId 
  ? await invoke("remote_read_dir", { serverId: activeServerId, path })
  : await invoke("read_dir", { path });

// ❌ 错误：前端直接访问文件系统
const entries = fs.readdirSync(path);  // 禁止！

// ❌ 错误：前端直接建立网络连接
const socket = new WebSocket(url);     // 禁止！必须通过 Rust
```

### 0.4 文件组织规范

```
src/                          # 前端（只做 UI）
  ├── apps/                   # 应用组件（FileManager, Terminal, Monitor）
  ├── shell/                  # 桌面外壳（Desktop, TopBar, Dock）
  ├── components/             # 通用 UI 组件（HeaderBar, Button）
  ├── context/                # React Context（状态管理）
  └── styles/                 # CSS 样式（Adwaita 设计系统）

src-tauri/src/                # 后端（系统操作 + 网络通信）
  ├── lib.rs                  # Tauri Command 注册
  ├── connection.rs           # 远程连接管理（QUIC/WebSocket）
  ├── pty.rs                  # 本地 PTY 管理
  └── ...                     # 其他系统操作模块
```

## 零、什么是「GNOME 迁移」

```
GNOME 桌面环境                      我们的远程控制客户端
─────────────                      ─────────────────────
Adwaita 设计系统        ──映射──→   CSS 变量 + React 组件库
GNOME Shell 布局        ──映射──→   Tauri 窗口管理器
GNOME HIG 交互规范     ──映射──→   React 组件交互约定
Adwaita 图标主题        ──复用──→   直接引用 SVG 图标
GNOME 应用 UX 模式     ──映射──→   文件/终端/监控/设置面板

GTK4 渲染引擎           ✗ 不迁移    (用 React + CSS 替代)
Mutter 合成器           ✗ 不迁移    (OS 原生窗口管理)
GJS 运行时              ✗ 不迁移    (用 V8 + React)
D-Bus 服务              ✗ 不迁移    (用 QUIC + Agent)
```

**迁移的是设计语言和交互哲学，不是代码。**

### 架构原则

| 原则 | 说明 |
|------|------|
| **每个「应用」= 独立 Tauri 窗口** | OS 原生窗口管理，不重复造 compositor |
| **桌面窗口是启动器** | 含面板 + Dock + 桌面图标，双击创建新窗口 |
| **GNOME HIG 全程合规** | HeaderBar、侧边栏、间距、字体、动画曲线 |
| **零远程渲染** | 所有 UI 像素由本地 React 渲染，远程只传结构化数据 |
| **视觉 = Adwaita** | 颜色、圆角、阴影、图标完全遵循 GNOME 设计规范 |

// 客户端 → Agent (QUIC Stream)
// 每 100 个文件 ~5KB JSON，秒级响应

interface ReadDirRequest {
  path: string;
  sort_by?: 'name' | 'size' | 'mtime';
  sort_order?: 'asc' | 'desc';
}

interface ReadDirResponse {
  entries: FileEntry[];
  total: number;
}

// 文件下载：独立 QUIC Stream，零拷贝 splice 传输

  direction: 'download' | 'upload';
}
// 响应: 4KB 头 (JSON metadata) + 原始字节流

**技术栈：**
```
本地 React (xterm.js)         Rust Tauri 后端           远程 Agent
    │                           │                          │
    │ onKey(evt)                │                          │
    │──────────────────────────→│                          │
    │                           │ russh Channel write      │
    │                           │─────────────────────────→│ → PTY stdin
    │                           │                          │
    │                           │                          │ ← PTY stdout
    │                           │←─────────────────────────│ russsh Channel read
    │ xterm.write(data)         │                          │
    │←──────────────────────────│                          │

    // 每个终端标签页 = 一个 SSH Channel (Subsystem PTY)
    // 每个标签页 = 独立的 QUIC Stream (保证有序)
```

## 六、传输协议

### 6.1 QUIC 双通道

```
┌─────────────────── QUIC Connection ──────────────────┐
│                                                       │
│  Stream 0-N (可靠有序, 自动重传)                      │
│  ┌─────────────────────────────────────────────────┐ │
│  │ · 文件列表请求/响应 (flatbuffers)                │ │
│  │ · 终端 I/O (xterm.js ↔ PTY)                    │ │
│  │ · 文件上传/下载 (splice 零拷贝)                 │ │
│  │ · 系统监控指标推送 (2s 间隔)                    │ │
│  │ · 认证 (TLS 1.3 + Agent Token)                 │ │
│  │ · 服务管理 (systemctl)                          │ │
│  └─────────────────────────────────────────────────┘ │
│                                                       │
│  Datagram (不可靠无序, 丢包不重传)                    │
│  ┌─────────────────────────────────────────────────┐ │
│  │ · 心跳包 (100ms)                                │ │
│  │ · 实时光标位置（未来远程桌面用）                  │ │
│  └─────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘
```

### 6.2 消息协议

```protobuf
// 所有消息用 protobuf（或 flatbuffers），一个 Stream 多路复用

syntax = "proto3";

message Envelope {
  uint32 request_id = 1;       // 请求-响应匹配
  oneof payload {
    ReadDirRequest read_dir = 10;
    ReadDirResponse read_dir_resp = 11;
    FileTransferRequest file_transfer = 20;
    FileTransferAccept file_transfer_accept = 21;
    TerminalRequest terminal = 30;
    TerminalData terminal_data = 31;
    MetricsSubscribeRequest metrics_sub = 40;
    MetricsSnapshot metrics_data = 41;
    SystemctlRequest systemctl = 50;
    SystemctlResponse systemctl_resp = 51;
  }
}
```

### 6.3 终端通道的特殊处理

终端输出不经过 protobuf 序列化——直接发原始字节：

```
Stream: 终端会话 N
  |
  ├── 4 字节: 终端 ID (session_id, u32 LE)
  ├── 1 字节: 方向 (0=stdin 键盘, 1=stdout 输出)
  ├── 4 字节: 数据长度 (u32 LE)
  └── N 字节: 原始 ANSI 转义序列

// 绕过 protobuf 的理由:
// - ANSI 转义序列不需要结构化
// - xterm.js 直接吃原始字节
// - 避免 copy + encode + decode 开销
```

## 八、安全模型

### 8.1 认证流程

```
首次连接:
  客户端                             Agent
    │                                  │
    │──── QUIC connect (no token) ────→│
    │←── Challenge (random nonce) ────│
    │──── 用户输入 SSH 密码或密钥 ────→│ (Agent 临时用 SSH 连接验证)
    │←── Agent Token (永久) ──────────│ (客户端加密存储)
    │                                  │

后续连接:
    │──── QUIC connect + Token ───────→│
    │←── 0-RTT 已连接 ────────────────│
```

### 8.2 权限模型

```rust
// Agent 内部权限检查
enum Operation {
    ReadDir,
    ReadFile,
    WriteFile,
    SpawnPty,
    Systemctl,
    ReadProcFS,     // 系统监控
}

fn check_permission(op: Operation, path: &str) -> bool {
    match op {
        ReadDir | ReadFile => {
            // 只允许 allowed_paths 白名单
            ALLOWED_PATHS.iter().any(|prefix| path.starts_with(prefix))
        }
        WriteFile => {
            // 写操作额外要求不在系统关键路径
            !path.starts_with("/etc/") || path.starts_with("/etc/nginx/")
        }
        SpawnPty => {
            // PTY 默认在 /home 下工作
            true  // PTY 本身不传路径，Agent 用 low-privilege 用户运行
        }
        Systemctl => {
            // 只允许 status/restart，不允许 stop 关键服务
            !is_critical_service(path)
        }
        ReadProcFS => true,
    }
}
```

## 附录 B：为什么不用 GTK4 而是 React

GTK4 是优秀的原生 GUI 库，但在远程控制场景下：
- GTK4 需要系统运行 X11/Wayland display server
- GTK4 渲染输出是像素（跟云桌面一样）
- GTK4 不能嵌进 Tauri WebView
- GTK4 的 CSS 系统与 Web CSS 不兼容

用 React 渲染的好处：
- 直接跑在 Tauri WebView 里，零额外依赖
- CSS 完全兼容 Web 标准
- 复用 Adwaita 设计令牌（颜色/间距/字号）而非 GTK 代码
- 未来如果需要 Web 版客户端，React 组件可直接复用
